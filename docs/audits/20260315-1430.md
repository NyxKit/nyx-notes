# Nyx Notes Core Audit — 20260315-1430

---

## 1. Executive Summary

The project is architecturally sound. The crate boundaries are clean, the domain model is well-designed, and the separation between storage, auth, and HTTP layers is correct. The filesystem-as-source-of-truth approach is executed consistently.

However, there are two issues that go beyond code quality:

1. A **live user-facing bug** existed in the auth extractor (`local_user()` hardcoded to `"local"`, ignoring `NOTES_USER_ID`) — fixed in the current session but only discovered through user testing, not caught by any test.
2. **Zero automated tests exist** across all five crates and the frontend, despite a documented test strategy. Every correctness claim is currently held up by manual testing alone.

A third area of concern is a **path traversal risk** in note file resolution: user-supplied note IDs are joined to a filesystem path without sanitization. On a self-hosted server this is a real attack surface.

The frontend is in early stages (layer 5 of 8) and has several correctness gaps that would surface the moment a non-local auth mode is used.

## 2. Severity Overview

### Critical

#### C1 — Path traversal in note ID → file path construction
**Severity:** Critical
**Why it matters:** A crafted note ID containing `../` components can escape the vault directory and access arbitrary files on the server.
**Evidence:** `crates/notes-storage-fs/src/lib.rs` — `load_note` and `save_note` both do:
```rust
let note_path = vault_dir.join(format!("{id}.md"));
```
`id` arrives from the URL path parameter (`/api/vaults/:vault_id/notes/:id`) with no sanitization. `Path::join` does not reject `..` components.
**Recommended fix:** Reject any `id` containing `/`, `\`, or `.` before the extension. A simple validation in the API handler layer:
```rust
if id.contains('/') || id.contains('\\') || id.contains("..") {
    return Err(AppError::UnprocessableEntity("invalid note id".into()));
}
```
Or use [`Path::file_name`](https://doc.rust-lang.org/std/path/struct.Path.html) to assert the resolved path stays within `vault_dir`.
**Breaking:** No.

---

#### C2 — `local_user()` hardcoded to `id: "local"` (recently fixed)
**Severity:** Critical (was live; fixed this session)
**Why it matters:** The server always resolved vault storage under `users/local/` regardless of `NOTES_USER_ID`, making CLI-created notes permanently invisible to the browser frontend.
**Evidence:** `crates/notes-server-axum/src/auth_extractor.rs` — `local_user()` constructed a `User` with `id: "local".into()` rather than reading from `LocalAuthStore`.
**Fix applied:** `from_request_parts` now calls `state.auth.verify_token("")` in local mode, returning the configured user.
**Root cause of survivability:** No tests. The bug was in the project since day one and was only caught by manual testing.
**Breaking:** No.

### High

#### H1 — Zero test coverage
**Severity:** High
**Why it matters:** A test strategy is fully documented in `docs/testing/README.md` but no test files exist in any crate or the frontend. Every correctness claim — frontmatter round-trips, permission enforcement, vault ownership checks, auth token validation — is untested. The C2 bug above is a direct consequence.
**Evidence:** No `#[cfg(test)]` blocks or `tests/` directories across all five crates. No `.spec.ts` or `e2e/` files in the frontend.
**Recommended fix:** Start with `notes-storage-fs` integration tests (highest risk, pure I/O, no async complexity) and `notes-server-axum` HTTP tests for permission enforcement. A `tempdir`-based round-trip test would have caught C2 immediately.
**Breaking:** No.

---

#### H2 — `update_note` does not verify vault ownership
**Severity:** High
**Why it matters:** The permission check in the `update_note` handler confirms the requester is the note's author, or that the vault has `Edit` permission. But it does not verify the vault belongs to the requesting user. Any user who knows a vault ID with `Edit` permission can modify notes in that vault, including vaults belonging to other users.
**Evidence:** `crates/notes-server-axum/src/routes/notes.rs` — `update_note` loads the vault to check permission but does not assert `vault.owner == VaultOwner::User(user.id)` for personal vaults.
**Recommended fix:** After loading the vault, add a membership/ownership assertion before proceeding to the note-level permission check. The pattern already exists in `delete_vault`:
```rust
match &vault.owner {
    VaultOwner::User(uid) if uid == &user.id => {}
    VaultOwner::Team(team_id) => { /* check team membership */ }
    _ => return Err(AppError::Forbidden),
}
```
**Breaking:** No — this is a tightening of existing enforcement.

---

#### H3 — Stale vault and note state not cleared on logout
**Severity:** High
**Why it matters:** `useAuth.logout()` clears `token` and `currentUser` but leaves `vaults` and `notes` module-level refs populated. After re-login as a different user, the previous user's data flashes in the UI before the next fetch completes. In a multi-user scenario on the same browser, this leaks data.
**Evidence:** `frontend/src/composables/useAuth.ts` — `logout()` does not call `useVaults().vaults.value = []` or `useNotes().notes.value = []`.
**Recommended fix:** Call reset functions on logout, or emit a global `auth:logout` event that composables listen to.
**Breaking:** No.

### Medium

#### M1 — Login request field naming mismatch: frontend vs. backend
**Severity:** Medium
**Why it matters:** `SecretKeyAuthStore::login` takes a `username` and `password`. The backend `LoginRequest` struct in `types.rs` has fields `username` and `password`. However, `LoginView.vue` uses `NyxInputType.Email` for the first input — suggesting the field might be sent as `email`. If the frontend submits `{ email, password }` instead of `{ username, password }`, login will silently fail with a deserialization error or a `UserNotFound`.
**Evidence:** `crates/notes-server-axum/src/types.rs` — `LoginRequest { username, password }`. `frontend/src/views/LoginView.vue` — uses `NyxInputType.Email`.
**Recommended fix:** Confirm the frontend submits `username` not `email` in the request body. If the field is `email` in the frontend, rename `LoginRequest.username` to `LoginRequest.email` in the backend and update `SecretKeyAuthStore` accordingly, for consistency.
**Breaking:** Breaking change to the login API if renamed.

---

#### M2 — `.users.json` stored inside `NOTES_ROOT`
**Severity:** Medium
**Why it matters:** In `secret_key` mode, the user database (including Argon2 password hashes) lives at `$NOTES_ROOT/.users.json`. If `NOTES_ROOT` is exposed via any static file server (e.g., nginx serving the notes directory for file sharing), this file is world-readable. The dot prefix provides no real protection.
**Evidence:** `crates/notes-auth/src/secret_key.rs` — `load_users` / `save_users` read from `root.join(".users.json")`.
**Recommended fix:** Move the users file to `$NOTES_ROOT/auth/.users.json` (still in root, but at least segregated) or to a separate path (e.g., `~/.config/nyx-notes/users.json`). Document the risk in `docs/architecture/authentication.md`.
**Breaking:** Migration required for existing `secret_key` users.

---

#### M3 — JWT key rotation is silent and undocumented
**Severity:** Medium
**Why it matters:** `load_or_generate_key` silently generates a new key if `~/.config/nyx-notes/secret.key` is absent. Key loss (e.g., running the server on a different machine, or the file being deleted) silently invalidates all existing tokens and forces all users to re-login with no warning.
**Evidence:** `crates/notes-auth/src/secret_key.rs` — `load_or_generate_key`.
**Recommended fix:** Log a prominent warning when generating a new key. Document key backup as a required operational step in `docs/architecture/authentication.md`. Consider emitting an error (not a silent generate) if `NOTES_SECRET_KEY` is unset in a production context.
**Breaking:** No.

---

#### M4 — `oidc` mode panics at startup instead of graceful error
**Severity:** Medium
**Why it matters:** Setting `AUTH_MODE=oidc` causes an unconditional `panic!()` at server startup. For a self-hosted server this means a silent crash rather than a clear startup error and usage guidance.
**Evidence:** `crates/notes-server-axum/src/main.rs:43` — `panic!("AUTH_MODE=oidc is not yet implemented...")`.
**Recommended fix:** Replace `panic!` with `eprintln!` + `std::process::exit(1)`. The message is good, the mechanism is not.
**Breaking:** No.

---

#### M5 — `ofetch` non-2xx responses produce untyped string errors in the frontend
**Severity:** Medium
**Why it matters:** All composables catch errors with `error.value = String(e)`. `ofetch` throws a `FetchError` with a structured body, but `String(e)` produces something like `"FetchError: ..."` — not the API error message. Users see useless error strings.
**Evidence:** `frontend/src/composables/useVaults.ts`, `useNotes.ts` — all catch blocks use `String(e)`.
**Recommended fix:** Import `FetchError` from `ofetch` and extract `e.data?.message` or `e.statusMessage` in a shared error handler utility.
**Breaking:** No.

---

#### M6 — Stored "last note" in localStorage not guarded against 404
**Severity:** Medium
**Why it matters:** `HomeView.vue` restores the last vault/note from `localStorage` on load. If the note or vault was deleted (e.g., via the CLI), the router navigates to a non-existent route. The `loadNote` call will throw, but the composable's `error` ref is not surfaced to the user — it silently shows "Select a note".
**Evidence:** `frontend/src/views/NoteView.vue` — `localStorage.setItem(LAST_NOTE_KEY, ...)`. `frontend/src/views/HomeView.vue` — restores on mount.
**Recommended fix:** Catch the 404 specifically in `loadNote` and clear the localStorage key, then redirect to the vault root.
**Breaking:** No.

### Low

#### L1 — Dead code warnings shipped in the binary
**Severity:** Low
**Why it matters:** `SecretKeyAuthStore.notes_root` is never read; `issuer` and `client_id` in the OIDC branch of `main.rs` are unused. These generate compiler warnings on every build.
**Evidence:** Build output in the session — two warnings from `notes-server-axum`, one from `notes-auth`.
**Recommended fix:** Prefix with `_` or remove. The `notes_root` field in `SecretKeyAuthStore` exists only to satisfy the constructor; if it's truly unused, remove it.

---

#### L2 — `StorageError::PermissionDenied` is dead code
**Severity:** Low
**Why it matters:** `FsStorage` never returns `PermissionDenied`. The permission model is enforced entirely in the API layer, making this variant permanently unused in the only `StorageBackend` implementation.
**Evidence:** `crates/notes-core/src/storage.rs` — `StorageError::PermissionDenied` defined. `crates/notes-storage-fs/src/lib.rs` — never returned.
**Recommended fix:** Either remove the variant or document it as reserved for future use (e.g., OS-level permission errors from `std::io::ErrorKind::PermissionDenied`). A future OS permission error would currently map to `StorageError::IoError`, losing the semantic.

---

#### L3 — `notes-server-axum` library crate depends on `notes-auth`
**Severity:** Low
**Why it matters:** The library crate (`notes-server-axum`) imports from `notes-auth` indirectly via `main.rs`. Acceptable for now, but it means adding `notes-auth-oidc` would require a new dependency in the binary. The lib crate itself (`AppState`, `routes`, `auth_extractor`) is already auth-agnostic (takes `Arc<dyn AuthStore>`) — only `main.rs` wires the concrete type.
**Evidence:** `crates/notes-server-axum/Cargo.toml`.
**Recommended fix:** This is fine for the current stage. Note it as an expected pattern in the architecture docs.

---

#### L4 — `save_team` auto-creates home vault as an undocumented side effect
**Severity:** Low
**Why it matters:** Calling `save_team` with an existing team (e.g., to update member list) will silently create a `home` vault if one doesn't exist. This is probably correct behavior, but it's surprising and untested.
**Evidence:** `crates/notes-storage-fs/src/lib.rs` — `save_team` body.
**Recommended fix:** Document the side effect in a code comment. Consider separating `create_team` and `update_team` methods in the trait if this becomes a source of bugs.

---

#### L5 — `find_vault_path` has no fast path and no caching
**Severity:** Low
**Why it matters:** Every note and vault operation scans all vault directories to resolve a vault ID. For a personal installation with 2–10 vaults, this is trivially fast. For a multi-user server with many vaults (future), it scales linearly.
**Evidence:** `crates/notes-storage-fs/src/lib.rs:49` — `find_vault_path`.
**Recommended fix:** Acceptable as-is for the current use case. If performance becomes a concern, an in-memory `HashMap<vault_id, PathBuf>` in `FsStorage` would eliminate the scan.

## 3. Backend Architectural Assessment

The crate boundaries are clean and reflect the intended layering:

- `notes-core` has zero runtime deps (only `chrono`, `serde`, `thiserror`) — correct for a domain crate.
- `notes-storage-fs` implements the `StorageBackend` trait fully. The sync trait + `spawn_blocking` in Axum is the right call: the CLI needs sync, the trait is object-safe, and local filesystem I/O is fast enough.
- `notes-auth` is correctly isolated. `LocalAuthStore` and `SecretKeyAuthStore` are independent and the crate has no knowledge of HTTP.
- `notes-server-axum` is the composition root. `AppState` holds `Arc<dyn StorageBackend>` (via adapter) and `Arc<dyn AuthStore>` — both pluggable at startup. This is the correct pattern.
- `notes-cli` uses `FsStorage` directly without the async adapter — correct. No server dependency.

The `AuthConfig` enum in `types.rs` is used for mode-specific branching in the extractor — it mirrors the auth store type but is separate from it. This is slightly redundant (the extractor could call `verify_token` in all modes) but it makes the mode explicitly visible in the response type (`GET /api/auth/mode`). Acceptable.

One genuine layering concern: **permission checks live in `routes/notes.rs` and `routes/teams.rs`**, not in `FsStorage`. This is correct per the documented architecture, but it means `FsStorage` can be called directly (e.g., from CLI) without any permission enforcement. The CLI assumes it runs as the configured user — this is by design, but it means the `StorageBackend` trait should not be treated as safe to expose to arbitrary callers.

## 4. Storage and Filesystem Assessment

`FsStorage` is correct for its scope. Key observations:

**Vault resolution** — The O(n) scan in `find_vault_path` is called on every note operation. It works by reading `.vault.json` files, which is reliable but slow for large installations. The ID-based lookup is the right design (slugs can change, IDs cannot), but the implementation has no caching.

**Frontmatter parsing** — `serde_yaml` parses YAML frontmatter. This is robust but `serde_yaml` has known edge cases with special string values (e.g., `yes`/`no` as booleans, bare timestamps). Notes with unusual titles or tag values could fail to parse. A frontmatter format using a stricter subset (TOML or JSON) would be more predictable, but changing this is a breaking format change.

**Note ID → file path** — See C1 above. This is the highest-priority fix in the storage layer.

**`list_notes` sort** — Sorts by `updated_at` descending. Correct.

**`delete_vault` has notes guard** — Checks for `.md` files before deleting. Correct. But it doesn't check for subdirectories, which shouldn't exist but could if the user manually creates them.

**Atomicity** — No write-ahead or atomic rename is used. A crash mid-write could corrupt a note file. For a personal notes app this is acceptable, but worth noting.

## 5. API and Auth Assessment

**Route structure** is consistent and RESTful. Verb and status code usage looks correct (`201 CREATED`, `204 NO_CONTENT`).

**Auth extractor** — After the C2 fix, `local` mode correctly delegates to `LocalAuthStore.verify_token`. All other modes require a `Bearer` token. The extractor is clean.

**Permission enforcement** — Notes routes check:
- `list_notes`: filters by `permission != Restricted || vault.permission != Restricted || user is author` — correct.
- `get_note`: author or non-restricted — correct.
- `update_note`: author or `Edit` permission — missing vault ownership check (H2).
- `delete_note`: author or vault/team owner — needs verification.
- `patch_note_permission`: author only — correct.

**Team routes** — `require_role` helper enforces `Owner > Admin > Member` hierarchy. `add_member` prevents assigning the `Owner` role. No check prevents removing the last `Owner` from a team — this could orphan the team permanently.

**`AppError` to HTTP mapping** — Clean. Internal errors return 500 without leaking filesystem paths (the `String` in `AppError::Internal` comes from `StorageError::IoError(e).to_string()` which may include file paths). Worth verifying this doesn't leak paths in the `IoError` case.

**Login endpoint availability in all modes** — `POST /api/auth/login` is registered regardless of `AUTH_MODE`. In `local` mode, `LocalAuthStore` doesn't implement `login`, so the call returns `AuthError::ServiceError` → 500. This is confusing — a 405 or 404 would be more appropriate. Alternatively, filter the route based on auth mode in `routes/mod.rs`.

## 6. CLI Assessment

The CLI is well-structured. Direct `FsStorage` access is the right call — no server required for local workflows.

**Config layering** — `CliConfig` loads from TOML then overlays env vars. This is correct and the precedence is sensible.

**`edit` command** — Opens the `.md` file in `$EDITOR` and should update `updated_at` on return. This requires re-reading the file after the editor closes and patching the frontmatter — verify this is actually implemented and that it handles parse errors from external edits gracefully.

**`resolve_vault`** — If `NOTES_VAULT` is not set and no `--vault` flag is passed, behavior should default to the `home` vault. Verify the fallback is explicit and documented.

**Error messages** — CLI uses `anyhow`, so errors propagate with context. This is good for development but may produce overly verbose messages in normal use. No user-facing error formatting has been applied yet.

**No auth in CLI** — By design. But this means CLI operations bypass all permission checks. A note marked `Restricted` in a shared team vault can be read directly via CLI by anyone with filesystem access.

## 7. Frontend Assessment

The frontend is at layer 5 of 8. The composables and API client are correctly structured. Key gaps:

**State management** — Module-level refs are the correct pattern for this project (globally shared, no Pinia needed). But the lifecycle of these refs is not managed: they are never reset on logout (H3) and can hold stale data across vault switches.

**`useNotes.notes` is flat** — The notes list is a single flat array, not keyed by vault. Switching vaults replaces the array (`loadList(vaultId)` overwrites `notes.value`). This works for single-vault-at-a-time navigation, but if `NoteList.vue` renders while a load is in progress, it briefly shows the previous vault's notes.

**API client** — `ofetch` client is clean. The `onRequest` hook for token injection is correct. No response interceptor for global 401 handling (auto-logout on session expiry). This will be needed when `secret_key` mode is used.

**TypeScript types** — The `types/index.ts` file mirrors the Rust domain types closely. One concern: `VaultOwner` is defined as a tagged union `{ type: 'user' | 'team', id: string }`. This matches the Rust `#[serde(tag = "type", content = "id")]` serialization. Correct.

**`useTeams.ts`** — Very thin (17 lines). Only loads teams and provides a `teamName(teamId)` helper. The `VaultSwitcher` uses this to group vaults. This is minimal but sufficient for layer 5.

**Router guard** — Discovers auth mode once, skips login for `local` mode. The `discoverMode()` call is async; if it fails (server down), the guard doesn't handle the error — navigation hangs.

## 9. Testing Assessment

**Current state:** No tests exist anywhere in the project.

**Highest risk areas with no coverage:**
1. `frontmatter::parse_note_file` / `serialize_note_file` — round-trip correctness for edge cases (empty body, special characters in titles, missing optional fields)
2. `FsStorage` — vault CRUD, note CRUD, team membership, vault resolution
3. Permission enforcement in `routes/notes.rs` — the most complex business logic in the project
4. `SecretKeyAuthStore` — login, token issuance, token verification, key rotation
5. Auth extractor — correct user resolution in each mode

**Suggested starting point:**
```rust
// crates/notes-storage-fs/tests/integration.rs
#[test]
fn round_trip_note() {
    let dir = tempfile::tempdir().unwrap();
    let storage = FsStorage::new(dir.path());
    // create vault, save note, load note, assert fields match
}
```

**Why no tests exist:** The project was scaffolded quickly in an incremental AI-assisted session. The test strategy is documented correctly but implementation was deferred. This is the single highest-leverage improvement.

## 12. Refactor Roadmap

### Phase 1 — Quick wins (no breaking changes, low effort)

- Fix C1: sanitize note IDs before path construction
- Fix H2: add vault ownership check in `update_note`
- Fix M4: replace OIDC `panic!` with graceful exit
- Fix H3: clear composable state on logout
- Add global 401 interceptor in `api/client.ts`
- Remove dead code warnings (`notes_root`, `issuer`, `client_id`)
- Document key rotation risk and `.users.json` exposure in auth docs

### Phase 2 — Structural (moderate effort, no breaking changes)

- Write `notes-storage-fs` integration test suite (tempdir-based)
- Write `notes-server-axum` HTTP test suite (axum `TestServer`)
- Write CLI subprocess tests on tempdir `NOTES_ROOT`
- Write frontend composable unit tests (Vitest + `ofetch` mocks)
- Add `FsStorage` ID validation as a helper used by all note methods
- Add last-owner-removal guard to team member delete route
- Fix `AppError::Internal` to avoid leaking filesystem paths

### Phase 3 — Breaking / larger changes

- Resolve `username` vs `email` naming in login API
- Move `.users.json` to a non-`NOTES_ROOT` path with migration tooling
- Implement OIDC auth mode (`notes-auth-oidc` crate)
- Add `NyxEditor` integration (Layer 6) — blocked on nyx-kit
